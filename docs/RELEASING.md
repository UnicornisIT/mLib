# Выпуск релиза mLib

Инструкция описывает выпуск Windows Desktop-версии mLib (`vX.Y.Z[-alpha]`). Она сверена с
`.github/workflows/windows-desktop.yml`, `.github/workflows/ci.yml` и `scripts/check_release.py`.
Если вы меняете workflow, обновите этот файл в том же pull request.

## 1. Главное правило

**Опубликованный тег не переиздаётся.** Тег `v<версия>`, однажды появившийся в `origin`, не удаляют,
не переносят на другой коммит и не создают повторно. Любое исправление опубликованного выпуска выходит
следующей версией (`0.0.4-alpha` → `0.0.5-alpha`).

**Теги вручную не создаются и не отправляются.** Тег создаёт сам GitHub в момент публикации Release
(раздел 2). «Голый» тег без Release попадает в ленту `releases.atom` первым, и electron-updater у всех
установленных копий получает 404 на `latest.yml`, пока не выйдет следующая версия.

Почему так строго: у одной версии не должно существовать двух разных сборок. electron-updater сравнивает
только номера версий, поэтому пользователь со «старой» сборкой той же версии никогда не получит
исправленную, а опубликованные SHA-256 перестанут совпадать с уже скачанными файлами.

Как это обеспечено:

- workflow падает, если Release (в том числе черновик) или тег для версии уже существуют, и проверяет
  это ещё раз непосредственно перед публикацией; `--clobber` и изменение опубликованных Releases из
  workflow убраны;
- в настройках репозитория включён ruleset `release-tags` для `refs/tags/v*`: *Restrict updates*,
  *Restrict deletions*, *Block force pushes*. *Restrict creations* должен оставаться выключенным — иначе
  GitHub не сможет создать тег при публикации Release из workflow. Workflow не может обнаружить
  удалённый Release, поэтому без ruleset правило держится только на дисциплине.

Упавшая сборка номер версии не «сжигает»: пока Release не опубликован, тега нет, и ту же версию можно
выпустить повторно после исправления в `main`.

## 2. Как устроен релиз

Релиз запускается вручную: `Actions → Windows Desktop → Run workflow` на ветке `main` с входами
`version` (без `v`, например `0.0.5-alpha`) и `publish` (флажок). Сборка идёт с коммита, на котором
стоял `main` в момент запуска (`GITHUB_SHA`); этот же коммит получит тег. Jobs выполняются
последовательно:

| Job | Runner | Что делает | Права токена |
| --- | --- | --- | --- |
| `verify` | ubuntu | при `publish` требует ветку `main` и непустой `version`; `scripts/check_release.py --tag v<version>`: все источники версии совпадают, есть release notes; ни Release, ни тега `v<version>` ещё нет | `contents: read` |
| `ci` | ubuntu | полный `ci.yml` через `workflow_call`: ruff, pytest, typecheck, lint, Next.js build, Playwright E2E, Docker build | `contents: read` |
| `installer` | windows | `scripts/build-windows.ps1` (повторно гоняет тесты, собирает backend, frontend и NSIS), загружает artifact | `contents: read` |
| `publish` | ubuntu | только при `publish` на `main`: проверяет имя установщика, ещё раз — отсутствие Release (включая черновики) и тега; создаёт **черновик** Release с вложениями (`gh release create --draft --target <sha>`), проверяет, что загружены все четыре файла, и публикует его (`gh release edit --draft=false`) | `contents: write` |

Черновик не виден в `releases.atom` и electron-updater, и тега у него ещё нет. Тег `v<версия>`
появляется на `<sha>` только в момент публикации — сразу вместе со всеми вложениями. Если что-то
падает до публикации, job удаляет свой черновик, и в репозитории не остаётся ни тега, ни Release.
После публикации job сверяет, что тег указывает на `<sha>`.

Release содержит четыре файла (плюс два архива исходников, которые GitHub добавляет сам):

- `mLib-Setup-<версия>-x64.exe`;
- `mLib-Setup-<версия>-x64.exe.sha256`;
- `mLib-Setup-<версия>-x64.exe.blockmap`;
- `latest.yml` — метаданные electron-updater с SHA-512.

Версия с суффиксом (`-alpha`) публикуется как **pre-release**, стабильная — как latest. Текст Release
берётся из `.github/release-notes/v<версия>.md`; без этого файла `verify` падает.

**Пробный запуск** — тот же `Run workflow` без флажка `publish` (на любой ветке). Он проходит `verify`,
`ci` и `installer`, создаёт artifact на 14 дней и **ничего не публикует**. Если указан `version`,
пробный запуск заодно проверяет release notes и то, что версия ещё свободна. Секреты подписи передаются
только при `publish`, поэтому пробная сборка неподписанная. Такой же пробный прогон (без `version`)
запускается автоматически в pull request, который меняет этот workflow, `scripts/build-windows.ps1`,
`scripts/check_release.py` или файлы сборки desktop (`package.json`, `package-lock.json`,
`electron-builder.config.cjs`).

Отправка тега workflow не запускает: триггера `push: tags` больше нет.

Во всех jobs `actions/checkout` работает с `persist-credentials: false`, а сторонние Actions закреплены
по SHA коммита. При обновлении Action меняйте SHA и комментарий с версией вместе.

Установленное приложение проверяет Releases через 15 секунд после запуска и затем каждые 6 часов.
Alpha-сборка видит новые prerelease, стабильная — только стабильные выпуски. Скачивание и установка
начинаются только после действий пользователя. Если первая запись ленты — выпуск без `latest.yml`
(`alpha.yml`) и GitHub отвечает 404, приложение не показывает ошибку: пишет «Новая версия ещё
публикуется» и повторяет проверку через 30 минут. Остальные ошибки показываются как раньше.

Отдельного релизного процесса для Docker/server-версии нет: образы в реестр не публикуются,
server-пользователи обновляются через `git pull` и `docker compose up -d --build`.

## 3. Версионирование

Semantic Versioning, сейчас схема `0.0.N-alpha`. Версия хранится в **пяти** файлах:

| Файл | Поле |
| --- | --- |
| `backend/app/core/config.py` | `app_version` |
| `frontend/package.json` | `version` |
| `desktop/package.json` | `version` |
| `desktop/frontend-runtime/package.json` | `version` |
| `desktop/package-lock.json` | `version` и `packages[""].version` |

Дополнительно для каждой версии нужны:

- `.github/release-notes/v<версия>.md` — текст GitHub Release (обязателен);
- запись в `frontend/src/lib/releaseNotes.ts` — окно «Что нового» после обновления (если записи нет,
  окно просто не показывается);
- раздел в `CHANGELOG.md`.

Проверка согласованности (её же выполняют CI и `verify`):

```bash
python scripts/check_release.py
python scripts/check_release.py --tag v0.0.4-alpha
```

`appId` в NSIS не меняется, поэтому новая версия ставится поверх старой, а данные в `%LOCALAPPDATA%\mLib`
сохраняются.

## 4. Чек-лист перед выпуском

1. Изменения слиты в `main`, CI на `main` зелёный, рабочее дерево чистое (`git status`).
2. Версия обновлена во всех пяти файлах, добавлены release notes, запись «Что нового» и раздел
   `CHANGELOG.md`; `python scripts/check_release.py --tag v<версия>` проходит.
3. Упоминания имени установщика в `README.md`, `docs/WINDOWS_DESKTOP_BUILD.md` и
   `docs/WINDOWS_DESKTOP_USER.md` обновлены.
4. Если есть новые Alembic-миграции, они проверены на копии реальной библиотеки. Перед миграцией desktop
   создаёт `backups/auto-before-migration-*.zip` — **только базы данных, без медиа** — и при ошибке
   откатывает базы из этой копии. Хранятся последние 7 таких копий.
5. Локальные проверки:

   ```bash
   cd backend
   python -m pytest
   ruff check app tests desktop_backend.py

   cd ../frontend
   pnpm typecheck
   pnpm lint
   pnpm build
   pnpm test:e2e
   ```

6. Пробная сборка: `Actions → Windows Desktop → Run workflow` на `main` с `version`, **без** `publish`,
   и скачать artifact, либо локально
   на Windows 11 x64 (Python 3.12, Node.js 22+ с Corepack):

   ```powershell
   .\scripts\build-windows.ps1              # с тестами
   .\scripts\build-windows.ps1 -SkipTests   # повторная сборка без тестов
   $env:MLIB_PYTHON = "C:\Python312\python.exe"   # если Python несколько
   ```

   Результат: `dist\mLib-Setup-<версия>-x64.exe`.
7. Ручная проверка установщика на чистой Windows 11 x64 VM без Python, Node, Git и IDE:
   1. установить EXE;
   2. создать пользователя и несколько записей с media, включая загрузку трека, книги и видео;
   3. перезапустить приложение, проверить сохранность данных;
   4. выполнить Export, Backup, Import и Restore (через интерфейс, а не только тестами);
   5. установить новую версию поверх старой; при наличии миграций убедиться, что показывается окно
      запуска и приложение стартует;
   6. проверить автообновление с Release большей версии (предложение → скачивание → перезапуск);
   7. удалить приложение, убедиться, что `%LOCALAPPDATA%\mLib` остался; установить повторно;
   8. проверить русский Unicode и масштабирование Windows 100/125/150/200%;
   9. убедиться, что после закрытия не остаётся процессов `mLib.exe` и `mlib-backend.exe`.

## 5. Выпуск

```bash
git switch main
git pull --ff-only
python scripts/check_release.py --tag v0.0.5-alpha
```

1. `Actions → Windows Desktop → Run workflow`: ветка `main`, `version` = `0.0.5-alpha`, флажок
   `publish` включён. Тег вручную **не** создавайте и не отправляйте.
2. Дождитесь зелёного прогона всех четырёх jobs. Пока идёт сборка, тега и Release нет, установленные
   копии продолжают видеть предыдущий выпуск.
3. `Releases`: появился pre-release с четырьмя файлами и текстом из `.github/release-notes/`; тег
   `v0.0.5-alpha` указывает на коммит, с которого запускался workflow.
4. Скачайте EXE и сверьте SHA-256 с опубликованной суммой.
5. На машине со старой версией убедитесь, что приложение предлагает обновление.
6. Локально: `git fetch --tags`.

Формат: лёгкий (lightweight) тег `v<версия>`, который GitHub создаёт при публикации Release, и заголовок
Release `mLib v<версия>` (его задаёт workflow). Выпуски до `v0.0.4-alpha` включительно помечены
аннотированными тегами, созданными вручную.

### Структура описания Release

Файл `.github/release-notes/v<версия>.md` строится по одному шаблону (образец — `v0.0.4-alpha.md`):

1. `# mLib <версия> — <суть выпуска>` и строка: номер выпуска, платформа, дата.
2. Врезка о статусе alpha и совет сделать резервную копию.
3. `## Что нового`, `## Исправлено`, `## Безопасность` — пустые разделы не включать.
4. `## Известные проблемы` — честно, с указанием версии, где исправлено.
5. `## Установка и обновление` — с каких версий придёт автообновление, где хранятся данные.
6. `## Файлы выпуска` — таблица вложений и команда проверки SHA-256.
7. `## Изменения` — ссылка `compare/<предыдущий тег>...<тег>`.

Описания уже опубликованных Releases можно уточнять (это не меняет сборку), но вложения и тег — нельзя.
После правки проверьте, что в `https://github.com/<owner>/<repo>/releases.atom` первым по-прежнему
идёт самый новый выпуск: electron-updater берёт первую подходящую запись ленты.

## 6. Подпись установщика

Подписывается только публикуемая сборка: секреты `CSC_LINK` и `CSC_KEY_PASSWORD`
(`Settings → Secrets and variables → Actions`) передаются в job `installer` лишь при запуске с `publish`.
Без них EXE публикуется **неподписанным**, и Windows SmartScreen показывает предупреждение о неизвестном
издателе. Сертификат не хранить в репозитории, самоподписанный не использовать.

Ограничение текущей конфигурации: в `desktop/package.json` стоит `signAndEditExecutable: false`, поэтому
даже при наличии сертификата `mLib.exe` внутри установщика, вероятно, остаётся неподписанным.
После настройки сертификата проверьте `signtool verify /pa` для установщика и для установленных
`mLib.exe` и `mlib-backend.exe`.

Публикация использует встроенный `GITHUB_TOKEN`, отдельный токен не нужен. Репозиторий и Releases должны
быть публичными: токен приватного репозитория в приложение встраивать нельзя.

## 7. Если что-то пошло не так

| Ситуация | Действие |
| --- | --- |
| `verify` упал: версии не совпадают, нет release notes, запуск не с `main` | Тега и Release нет. Исправьте причину в `main` и запустите workflow с **той же** версией |
| `verify` упал: Release или тег `v<версия>` уже существуют | Версия занята. Поднимите версию (пять файлов, release notes, «Что нового», `CHANGELOG.md`) и запустите заново |
| `ci` или `installer` упали | Тега и Release нет. Исправьте в `main` и запустите с той же версией |
| `publish` упал до публикации черновика | Job сам удаляет свой черновик, тега нет. Проверьте `Releases`: если черновик `mLib v<версия>` всё же остался (например, прогон отменили), удалите его вручную — у черновика нет тега, его никто не видел. Затем запустите с той же версией |
| `publish` упал после публикации (тег указывает не на тот коммит, сбой сети после `--draft=false`) | Release и тег опубликованы. Не удаляйте и не переносите их; проверьте Release и, если он неисправен, выпустите следующую версию |
| Release опубликован, но сломан | Не удаляйте его и не меняйте вложения. Выпустите следующую версию с исправлением; в описании сломанного Release можно вручную добавить предупреждение |
| Кто-то вручную отправил тег `v*` без Release | Установленные копии получат 404 на `latest.yml`: приложение покажет «Новая версия ещё публикуется» и будет повторять проверку каждые 30 минут, но обновиться не сможет. Тег удалить нельзя (ruleset), а workflow с этой версией откажется работать. Как можно скорее выпустите следующую версию: её Release станет первым в ленте |

## 8. Прочие правила

- Первый installer с updater каждый пользователь ставит вручную; последующие обновления приходят сами.
- Не добавляйте в коммиты `.env`, базы, media, токены, логи и generated output.
- В сообщениях коммитов и описаниях PR не добавляйте строки `Co-Authored-By` и упоминания Claude.
  Это относится и к коммиту с обновлением версии, и к любым правкам при подготовке релиза.
